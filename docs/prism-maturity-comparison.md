# Prism 성숙도 및 상용 A/B 테스트 제품 비교

작성일: 2026-10-10

## 1. 현재 평가

**Prism은 MVP를 넘은 Spring 서비스용 사내 베타 단계다.** 실험 배정·노출 측정·전환 분석뿐 아니라 순차 분석, 베이지안 분석, 퍼널과 사용자 여정 분석까지 구현했다. 소규모 내부 실험의 도입을 검토할 수 있지만, 실제 운영 환경과 장애 상황을 검증한 뒤 적용 범위를 확대해야 한다.

상용 제품과의 큰 차이는 기능 개수보다 운영 신뢰성, 지원하는 지표·플랫폼의 범위, 여러 팀이 사용하는 관리 기능에 있다. 통계 기법의 이름이나 테스트 개수만으로 상용 제품과 동등한 성숙도를 판단하지 않는다.

상용 제품은 제품군과 요금제마다 지원 범위가 다르다. 아래 비교 기준은 각각의 제품에서 확인할 항목이며 모든 제품이 동일하게 제공한다는 의미는 아니다.

| 영역 | Prism의 구현 | 남은 차이와 제한 | 평가 |
|---|---|---|---|
| 실험 배정 | A/B/n 가중치 배정, 동일 사용자 배정 유지, 속성 타기팅, 참여율 확대, 예약, 상호 배제 레이어·전역 홀드아웃 | LOCAL/REMOTE 기능 차이, 익명·로그인 ID 통합 부재, QA 강제 배정 흐름 부족 | 핵심 기능 상당 부분 확보 |
| 측정 정확성 | 평가와 실제 노출 분리, 선행 노출·전환 귀속 검사, 고유 사용자 CVR, 이벤트 중복 처리, SRM·복수 변형 검사 | 일부 경로의 멱등성 제한, 수집 상태를 종합적으로 확인하는 화면 부족 | 설계 개선과 회귀 검증을 확보했으며 실환경 검증 필요 |
| 통계 분석 | Wilson 신뢰구간, 종료 후 전체 검정, 사전 분석 계획, 순차 분석, 베이지안 분석, 제한적 CUPED·세그먼트 | 표본 수·MDE·검정력 설계, 수치형·비율형 목표 지표, 고정된 최종 보고서 부족 | 전환 여부를 목표로 하는 실험에 유용 |

| 수집·운영 | 배치·재시도·flush, 설정 동기화, 선택적 Kafka 수집, durable inbox/outbox·DLQ·warehouse 토픽 출력 | 메모리 큐 유실, 설정 노후화 정책, 통합 모니터링·알림, 자동 중단, 부하·복구 검증 부족 | 가장 우선적인 개선 영역 |
| 팀·환경 관리 | API 키, 관리자·조회자 역할, BCrypt, CSRF, 변경 이력 | 프로젝트·환경·키 범위 분리, 여러 사용자·세분화 권한·SSO·승인 절차 없음 | 소규모 내부 운영에 맞춰져 있음 |
| 데이터 운영 | 전환·노출·분석 결과 저장, 외부 소비자가 사용할 수 있는 이벤트 출력 | 자동 보존·사용자 삭제, 자동 DB 마이그레이션, 외부 웨어하우스 연결 부족 | 운영 정책과 자동화 필요 |

### 통계 기능을 해석할 때의 제한

- 기본 종료 후 전체 검정과 고급 순차 분석은 서로 다른 분석이다. 기본 검정 결과를 반복 조회에 안전한 승자 판정으로 해석하면 안 된다.
- 순차 분석은 보수적인 confidence sequence를 사용하며 독립 사용자와 안정적인 군 평균 등의 가정이 있다. 분석 방식이 존재한다는 사실과 실제 사용 사례에서의 교정·검증 수준을 구분한다.
- 베이지안 분석은 대조군 대비 확률, 사후 구간, 기대 손실을 제공한다. 빈도주의 p-value와 같은 의미가 아니다.
- CUPED는 유효한 사전 지표와 표본 조건을 만족할 때 보정 효과와 근사 오차를 제공한다. 별도 유의성 판정은 없다.
- 현재 결과 지표의 중심은 사용자의 전환 여부다. CUPED baseline에 숫자를 전달할 수 있어도 매출·객단가·지연시간 목표를 지원하는 것은 아니다.
- 사전 등록 세그먼트는 기술 통계다. 사후 탐색에서 발견한 차이를 자동으로 인과 효과로 판정하지 않는다.

## 3. 제품별 비교

### GrowthBook

기술 중심의 실험 플랫폼이라는 점에서 Prism과 가장 가까운 비교 대상이다. 공식 공개 설명에는 다양한 SDK, SQL 기반 지표, 웨어하우스 연결, 기능 플래그, 순차·베이지안·CUPED 분석, 제품 분석과 공유 기능이 포함돼 있다.

Prism도 자체 운영과 고급 실험 분석의 기반을 갖췄지만, SDK·지표·데이터 소스의 범위는 훨씬 좁다. Prism의 선택 이유는 Spring 서비스에 맞춘 통합과 자체 데이터 통제에서 찾는 것이 적절하다. 분석 기법의 일부가 겹친다는 이유로 두 제품이 동등하다고 평가하지 않는다.

### Statsig

공식 JavaScript SDK 설명에서 A/B/n 실험, 기능 플래그, 동적 설정과 브라우저·React·React Native 연동을 확인할 수 있다. 웹 분석·세션 리플레이를 위한 패키지도 제공한다.

Prism은 서버에서 실험 로직을 구현하고 측정하는 기반이 있지만, 프런트엔드와 모바일까지 이어지는 적용 범위가 부족하다. 다만 SDK 지원 목록은 측정 정확성이나 성능의 직접적인 비교 근거가 아니므로, 실제 도입 시에는 원하는 사용 사례를 별도로 검증해야 한다.

### LaunchDarkly

기능 플래그와 출시 제어의 비교 대상으로 적합하다. 공식 SDK 설명에는 여러 언어 지원, 사용자 속성에 따른 기능 제공, 점진적 출시와 재배포 없이 기능을 중단하는 흐름이 소개돼 있다.

Prism도 참여율 확대·일시중지·종료 기능이 있지만, 형식 있는 flag 값 관리와 폭넓은 SDK 지원은 부족하다. 설정 동기화가 실패한 SDK는 마지막 정상 설정을 유지하므로 전역 중단 전파 시간과 실패 시 동작 정책도 검증·정의해야 한다.

### 비교 대상 선택

현재의 개발자 중심 방향에서는 GrowthBook·Statsig를 실험 제품의 주요 비교 대상으로, LaunchDarkly를 출시 제어·기능 관리의 비교 대상으로 삼는다. 추후 비개발자 사용성을 확대할 때는 Optimizely Web Experimentation 같은 시각적 편집 제품군을 별도 조사한다. 웹 편집 제품과 서버 SDK 제품은 사용자와 적용 방식이 다르므로 하나의 순위로 묶지 않는다.

## 4. 개발자 적용과 관리자 설정의 역할

현재 Prism에서 관리자 설정만으로 서비스의 화면이나 업무 동작이 자동 변경되지는 않는다. 개발자가 변형별 동작과 이벤트 측정을 구현한 뒤 관리자가 실험 조건을 운영한다.

| 주체 | 현재 수행하는 일 | 개선할 부분 |
|---|---|---|
| 개발자 | SDK·스타터 설정, 사용자 ID 결정, 변형별 전략 구현, 실제 노출·전환 측정, 필요 시 분석 메타데이터 전달 | 적용 검증, 잘못된 설정 진단, 이벤트 전송 상태 확인, 다른 플랫폼 SDK |
| 관리자 | 실험·변형·비중·목표 설정, 분석 계획 등록, 시작·중지·종료, 결과·퍼널·여정 조회 | 설계 안내, QA 대상 확인, 표본 수·기간 계산, 가드레일 알림, 보고서 공유 |
| 운영자 | 서버·DB·Kafka 구성, 수동 마이그레이션, 로그·DLQ 확인 | 운영 대시보드, 지표·알림, 자동 업그레이드·복구·보존 정책 |

Spring 개발자를 먼저 지원하고 이후 비개발자에게 확대한다는 방향에 맞춰, 먼저 개발자가 적용 결과를 쉽게 확인하게 만드는 것이 좋다. 통합 화면에서 설정 버전, 최근 노출·전환, 거절 사유, 큐 상태를 볼 수 있으면 관리자도 실험이 정상적으로 측정되고 있는지 확인할 수 있다.

## 5. 검증된 부분과 남은 운영 위험

### 확인한 검증 결과

- 최신 기본 회귀 테스트 326개 통과. 실패·오류·건너뜀 0건.
- SDK의 Gradle 모듈 메타데이터·Maven POM을 각각 사용하는 독립 Java 소비자 검증 통과.
- API/Admin 실행 JAR 빌드 통과.
- 전략 누락·검증 우회·잘못된 전략 등록, 트랜잭션 롤백·커밋 실패·완료 콜백의 측정 오류를 재현하고 로컬 브랜치에서 수정.

기본 테스트에는 실제 MySQL·Kafka를 사용하는 태그 테스트가 포함되지 않는다. 위 결과는 기능 회귀와 SDK 소비 가능성의 근거이며, 운영 처리량·가용성·복구 능력의 근거는 아니다.

### 검증 또는 개발이 필요한 부분

| 항목 | 현재 제한 | 운영 전에 확인할 내용 |
|---|---|---|
| 실제 인프라 | MySQL migration·Kafka 브로커 통합 검증 미실행 | 업그레이드, 이벤트 귀속, 재시도·DLQ·재처리 검증 |
| SDK 이벤트 전송 | 메모리 큐이므로 강제 종료 시 유실 가능. LOCAL의 성공 반환은 큐 등록을 의미 | 허용 유실 기준, 전송 상태·종료 처리, 필요 시 영속 큐 |
| 설정 전파 | 최대 stale 시간 정책 없음 | 설정 동기화 실패와 긴급 중단 시 동작·전파 목표 |
| 장시간 실행 | 기본 누적 노출 중복 제거 한도는 사용자×실험 100,000개이며 TTL 없음 | 예상 사용자 수, 메모리 사용량, 한도 도달 시 처리 |
| 분석 규모 | 경로 집계는 200,000 이벤트·5,000 경로 한도. 고급 분석 확정은 기본 30초마다 최대 500명 | 실제 데이터량에서 조회 시간·확정 backlog·DB 부하 |
| 운영 자동화 | 수동 DB 마이그레이션, CI·정식 릴리스 자동화 부족 | 배포 순서, 적용 버전 기록, 백업·복구 절차 |
| 데이터 정책 | 자동 보존·사용자 삭제 흐름 없음 | 귀속·중복 제거 기간을 고려한 보존·삭제 설계 |
| 타기팅 권한 | SpEL 규칙을 실행하는 신뢰 경계가 있음 | 비개발자·여러 팀으로 확대하기 전 허용 연산과 접근 권한 제한 |

## 6. 권장 개발 순서와 완료 기준

### 1단계 — 검증된 사내 운영 기반

최근 측정 오류 수정을 반영하고 실제 운영에 가까운 환경에서 검증한다.

- MySQL·Kafka 통합 검증과 대표 트래픽의 부하·장애 테스트를 수행한다.
- 수집 진단 화면에 최근 노출·전환, 거절 사유, 큐·재시도·DLQ 상태, 설정 버전을 표시한다.
- CI, 자동 마이그레이션 적용 기록, 백업·복구 절차를 마련한다.
- 설정 노후화·이벤트 유실·SDK 용량 한도의 정책과 알림을 정한다.

**완료 기준:** 정상 이벤트와 거절·유실·지연을 구분할 수 있고, 장애 후 복구·재처리 결과를 검증하며, 배포·DB 업그레이드 절차를 반복해서 재현할 수 있다. 처리량과 허용 지연·유실 기준은 예상 운영 규모를 바탕으로 정한다.

### 2단계 — 실험 의사결정 지원

실험 생성부터 결과 판단까지의 흐름을 보완한다.

- 기준 전환율·최소 검출 효과(MDE)·검정력·필요 표본 수·예상 기간의 설계 기능을 추가한다.
- 기본 고정 표본 검정과 고급 순차 분석의 판단 기준을 화면에서 구분한다. 표본 설계 계산은 선택한 분석 방식에 맞춰 검증한다.
- 매출·객단가·지연시간 등 수치형·비율형 지표를 추가한다.
- 가드레일 악화 알림, 필요 시 검증된 자동 중단 정책을 도입한다.
- 분석 설정과 데이터 범위를 기록한 재현 가능한 최종 보고서를 제공한다.

**완료 기준:** 실험 전에 목적·필요 데이터·판단 기준을 정하고, 종료 후 같은 분석 조건으로 결과를 재현할 수 있다. 새 지표와 판단 방식은 기준 데이터로 통계적 동작을 검증한다.

### 3단계 — 팀과 플랫폼 확대

Spring 적용 흐름이 안정된 후 여러 팀·플랫폼과 비개발자로 범위를 넓힌다.

- 프로젝트·개발/운영 환경·API 키 범위와 사용자 권한을 분리한다.
- 팀 사용자, 실험 승인, 보존·삭제 정책을 추가한다.
- 우선순위에 따라 브라우저·React SDK와 형식 있는 flag·설정값 관리를 제공한다.
- 적용 검증·실험 템플릿·보고서 공유를 개선하고 시각적 편집의 필요성을 별도 판단한다.

**완료 기준:** 서로 다른 환경·팀의 설정과 데이터가 섞이지 않고, 사용자가 권한 내에서 실험을 운영할 수 있다. 각 SDK의 배정·노출·전환 계약을 공통 테스트로 검증한다.

운영 기반과 실험 판단 흐름을 먼저 완성하는 것이 다음 성숙도를 높이는 데 가장 효과적이다. 퍼널·경로 분석의 추가 기능과 시각적 편집은 그 이후 사용 사례에 따라 우선순위를 정한다.

## 7. Spring 의존성을 줄이는 개발 방향

다음 내용은 리팩토링 전 코드 확인에 따른 구조 개선안이다. 이후 `refactor/framework-independent-sdk` 작업에서는 코어·SDK의 Spring 실행 의존성을 제거하고, 데이터 규칙과 평가기 주입, 선택적 SpEL 호환 모듈을 구현한다. 구체적인 적용·호환 계약은 [프레임워크 독립 SDK 안내](framework-independent-sdk.md)에 기록한다. 아래 사전 평가와 목표 구조를 구분한다.

### 리팩토링 전 의존성

SDK는 이미 Spring 애플리케이션 컨텍스트 없이 사용할 수 있다. HTTP 통신도 Spring WebClient가 아닌 JDK의 `java.net.http.HttpClient`를 사용한다. 독립 Java 소비자 검증도 이 방식으로 실행된다.

그러나 다음 의존성이 남아 있다.

- `prism-core`의 `RuleEvaluator`가 Spring Expression Language(SpEL)에 직접 의존하고 `TrafficSplitter`가 이 평가기를 직접 호출한다. SDK는 core를 통해 Spring 표현식 라이브러리를 전이 의존한다.
- 루트 빌드가 모든 모듈에 Kotlin Spring/JPA 플러그인과 Spring Boot BOM을 적용한다. 컴파일 플러그인·빌드 버전 관리와 실행 시 필요한 Spring 라이브러리는 서로 다른 의존성이지만, 모듈별 역할 구분이 부족하다.
- 전략 자동 탐색과 전환 어노테이션·트랜잭션 완료 추적은 Spring 스타터에 구현돼 있다. 다른 프레임워크에서는 명시적 SDK 호출과 업무 커밋 후 추적을 사용해야 한다.
- 전체 JVM 대상 버전이 21이다. SDK의 `HttpClient.shutdownNow()` 등도 JDK 21 API를 사용하므로 타깃 버전 설정만 낮추어 JDK 17 지원을 확보할 수는 없다.

### 목표 구조

Prism 서버가 사용하는 프레임워크와 Prism을 도입하는 서비스가 사용하는 프레임워크를 분리한다. API·Admin·JPA 구현은 Spring을 사용할 수 있으며, 도입 서비스에 필요한 기본 SDK와 배정 코어는 프레임워크 독립적인 JVM 라이브러리로 만든다.

| 구성 | 목표 역할 | Spring 의존 정책 |
|---|---|---|
| `prism-core` | 도메인 모델, 결정적 배정, 참여율·레이어·홀드아웃 평가, 타기팅 평가 인터페이스 | Spring 실행 의존성 제거 |
| 기본 타기팅 평가기 | 명시적으로 제한된 연산을 지원하는 버전 있는 규칙 형식 | 프레임워크 독립. 다른 언어로 같은 결과를 재현할 수 있는 계약 |
| SpEL 호환 모듈 | 기존 문자열 규칙의 검증·평가 | 선택적 Spring 의존성. 기존 규칙을 사용하는 구성에서 명시적으로 연결 |
| `prism-sdk` | 설정 동기화, 평가·노출·전환 API, 전송·재시도, 명시적 전략 등록 | Spring 컨텍스트·표현식 라이브러리 없는 기본 구성 |
| `prism-spring-boot-starter` | 자동 설정, Bean 전략 탐색, AOP, Spring 트랜잭션 연동 | Spring 전용 어댑터 |
| API·Admin·인프라 | HTTP 서버·관리 화면·DB·Kafka 운영 | 현재 Spring 구현 유지 가능 |

예를 들어 코어는 `TargetingEvaluator` 인터페이스에 의존하고, 외부에서 선택한 평가기를 전달하도록 바꾼다. Spring 스타터는 자동 등록을 담당하고 일반 JVM 서비스는 SDK를 직접 생성한다. 외부 트랜잭션의 성공 여부는 기본 SDK가 임의로 추정하지 않고, 프레임워크별 어댑터 또는 호출자가 커밋 후 전환을 기록한다.

### 구현 순서와 호환성 기준

1. **빌드 역할 분리:** Spring/JPA 컴파일 플러그인은 사용하는 모듈에만 적용한다. JSON·리플렉션 의존성도 필요한 모듈에서 선언한다. 라이브러리 버전 관리와 게시된 POM·Gradle 메타데이터를 함께 검증한다. 이 단계만으로 SpEL 실행 의존성이 없어지지는 않는다.
2. **코어 평가 분리:** 직접 연결된 `RuleEvaluator`를 평가 인터페이스와 SpEL 구현으로 나눈다. 기존 문자열 규칙의 동작을 보존하는 호환 모듈을 마련한다.
3. **독립 규칙과 SDK:** 새 규칙 형식을 명시적인 버전으로 도입하고 기본 SDK가 이를 평가하게 한다. 기존 SpEL 규칙은 자동 재해석하지 않는다. SDK·서버의 지원 형식과 업그레이드 순서를 확인한 뒤 새 형식을 사용한다.
4. **도입 범위 확대:** Spring 없는 JVM 소비자의 배정·타기팅·노출·전환·종료 처리를 검증한다. JDK 17 지원이나 Ktor·Quarkus 통합은 실제 수요에 따라 별도 검증한다. JavaScript·Python SDK에는 별도 구현과 공통 계약 검증이 필요하다.

**완료 기준:** 기본 SDK 소비자의 런타임 의존성에 Spring이 없고, 독립 Java 프로젝트에서 전체 측정 흐름이 실행되며, 기존 Spring 구성과 SpEL 실험의 배정·타기팅 결과가 유지돼야 한다. 해시·버킷·사용자 ID 인코딩·시간·규칙 의미를 공통 기준 데이터로 검증한다. 지원하지 않는 규칙을 무시하고 전체 사용자에게 실험을 적용하지 않으며, 평가 오류와 정상적인 대상 제외를 구분해 진단한다.

이 구조는 Spring의 편의 기능을 유지하면서 다른 서비스의 도입 부담을 줄이는 데 목적이 있다. 서버 전체 재작성보다 코어·SDK·프레임워크 어댑터의 경계를 먼저 정리하는 것이 현재 코드에 적합하다.
